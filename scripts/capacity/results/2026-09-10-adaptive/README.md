# 扫描查询、调度与自适应并发验证

最终实现通过 32、128、512 项的三种并发模式对照，以及 2740 项自适应容量验证。2740 项两轮用时 **374.39 / 354.68 秒**，整个运行（含接口与空闲测量）**761.36 秒**，在 1200 秒预算内正常退出。每轮实际处理 2740 项，失败与待选择均为 0，最终全部媒体源为 Probed。

十个最终隔离数据库均通过 quick_check 和外键检查；源文件摘要不变，三张图片资产表及资产文件数保持 0。完整数据见 `validated-*.json` 与 `catalog-audit.json`。

自适应控制已验证可扩缩容，但这些样本没有证明它稳定快于单并发。主要收益来自查询和调度等待修复；不能把修复前后的全部时间差解释成并行加速。

## 实现与适用范围

父扫描、后台项目和存储校验的续租与工作执行保持同时推进。此前续租分支会暂停工作，工作若持有 SQLite 唯一连接，续租无法取得连接，超时后等待五分钟租约自然到期。针对单连接 SQLite 的回归在旧算法上退出 101，修复后通过；真实续租失败仍停止工作。修复前 2740 项虽在 888.34 秒内完成，但两轮各被重新领取一次，并出现超过 200 秒的后台空档，见 `lease-recovery-before.json`。

查询优化把单项目的存储根匹配改为独立子查询，避免对根内库存反复展开；迁移 079 补充反向身份匹配及 publication 媒体定位索引。扫描目标按 128 项游标分页，批量读取问题状态。子任务完成后合并通知父扫描，保留定时兜底及租约、版本、发布状态检查；修复子任务刚完成时读取旧状态的竞态。

后台扫描改为有上限的任务池，默认 `TJXY_SCAN_CONCURRENCY=auto`，支持 1–8 的固定目标上限。每 2 秒结合积压、CPU、可用内存、数据库与前台请求延迟调整：连续健康样本才逐次增加，扩容 10 秒后吞吐没有至少 5% 改善会回退并冷却 30 秒；压力过大时减半。数据库驱动 SQL 与完整任务领取事务分别计算 P95，避免大量快速语句掩盖连接池等待。CPU 采样缺失或过期时退回 1。固定模式同样受压力保护，因此配置为 4 不等于始终四并发。

后台探测有独立 CPU 上限（至多 4），为前台保留解析名额；存储读取也保留前台额度。调度按任务中已记录的存储根归属轮转，多个根活跃时限制单根占用；未记录根归属的任务共用一个分组，不代表对所有探测任务都实现了逐根公平；缩容不取消已开始的工作。SQLite 领取串行执行，写入仍受 SQLite 单写者约束。

## 测量方法与解释

使用 TMP 新建的独立 SQLite 数据库、回环服务与 Rust 1.88.0 release 构建。32/128/512/2740 容量库为极小的确定性 MP4、NFO、PNG，适合观察目录、SQL 与调度成本，不代表真实大片传输或解码吞吐。另一个 128 项播放库使用可解码的 12 秒 1280×720 H.264/AAC，每份 6,267,913 字节。没有清空系统页缓存，主机其他进程负载不可控，各模式单次运行，不是统计显著性或性能 SLA。

`experiment-summary.json` 保留各阶段结果与原始 TMP JSON 的 SHA256，省略重复的逐表索引容量和中间时间序列。历史文件名 `final-*` 是中间迭代，`verified-*` 是独立领取延迟修订后、续租修复前的数据；最后实现的数据以 `validated-*` 为准。最终 JSON 仅省略逐表索引 payload，保留扫描计数、SQL 模板统计、资源峰值及并发时间序列，不含 SQL 参数或测试凭据。

基线 128 项两轮为 102.03/104.69 秒；基线 32/512 项触发“ProbeMedia 已完成但尚未观察到发布”的竞态，均是失败运行。查询与唤醒修复后、尚未加入自适应池时，512 项为 24.05/22.70 秒，2740 项为 181.29/209.01 秒。由此可见主要已证实收益来自查询、分页与等待修复，不能把全部收益归因于并发。

中间矩阵已经覆盖 32、128、512 项的单并发、上限 4、自适应。主机不是隔离基准环境；同样的 SQL 语句数量可出现数倍执行时间差异，影响因素未完全分离，早期矩阵还与编译重叠。部分旧记录因 `du` 遇到 SQLite 临时 journal 删除而停止资源采样，其 RSS 峰值可能低估；最终脚本已重试并保留资源守卫。中间 2740 自适应运行在反馈修订前主动中止，不能算容量通过。

最终 128 项三种配置实际都只观察到 1 个槽位，因此 33.9 秒与约 8 秒的差异不是四并发收益。三组领取查询数量接近（11870/11848/11838），但驱动累计耗时分别约 1329/212/212 ms；这些样本不能隔离配置与运行环境对耗时的影响。

`job_stages.sum_first_claim_to_completion_ms` 包含等待、重试及异步交错，不能相加当作纯 CPU 时间。任务创建到领取也包含排队。SQL 是驱动语句计数，不是数据库事务率。扫描结果的 `failed=0` 指本轮项目结果；历史 `DiscoverTitles` 可能因 fixture 配置库策略后原调度版本过期而失败，不代表数据库内从未存在 Failed 任务。

## 压力控制与播放

下面的 CPU 压力和浏览器数据来自本轮较早的自适应版本；最终续租修订未更改播放路由，但这些数据不是对最终二进制的再次浏览器实测。最终版本另外重新执行完整 Rust 检查与全部容量矩阵。

实际 CPU 压力实验在后台达到 2 个槽位后，启动 16 个短时计算进程。采样 CPU 达 100%，槽位从 2 降到 1；负载移除后又逐步恢复到 2、3、4。证据见 `cpu-stress-observation.json`。该实验的外层测量进程在 180 秒被中断，第一轮完成、第二轮未完成，因此只证明缩容与恢复，不能当作完整容量通过。低内存、数据库延迟、前台延迟、采样过期、冷却和吞吐回退另外使用确定性控制器测试验证，没有故意耗尽主机物理内存。

在根校验结束、实际观察到 128 个后台项目任务时，执行 1/5/20 并发的 64 KiB Range 共 20/25/100 次，响应字节全部匹配；P95 为 44.49/54.58/102.61 ms。HEAD 无正文及长度、越界 416、图片 304 均通过。静音浏览器连续 10 次实际解码，首帧 368.1–549.4 ms，暂停及跳转第 8 秒续播通过，见 `playback-item-phase.json`。该测试覆盖项目处理阶段，并不覆盖整轮扫描所有阶段。

尚未满足全流程无读取中断：根校验期间，存储对象事实版本领先已提交的根版本，已有读取校验会暂时拒绝请求。一次观测为 264 个 Range 中 20 个 404，另观察到图片 503；用加入自适应前的服务复现为 220 个 Range 中 13 个 404。这是已存在的版本发布问题，本轮没有放宽读取校验来掩盖它。修复需要进一步处理校验期间的已提交事实与路径快照。

本机有声播放虽收到首帧，但媒体时钟停滞；静音或音量为零时正常推进，headed/headless 均有此现象。原因尚未确诊，不能声称音频输出或有声端到端播放通过。静音解码结果与上述限制分别记录在 `browser-muted.json`、`known-read-limitations.json`。

## 复现

```sh
cargo +1.88.0 build -p tjxy-server --example capacity_server --release --locked
python3 scripts/capacity/run.py --root /tmp/tjxy-new-512-auto --items 512 --scan-concurrency auto --concurrency 1 --idle-seconds 0 --max-seconds 300 --server-binary target/release/examples/capacity_server --report /tmp/tjxy-new-512-auto.json
python3 scripts/capacity/run.py --root /tmp/tjxy-new-2740-auto --items 2740 --scan-concurrency auto --concurrency 1 --max-seconds 1200 --server-binary target/release/examples/capacity_server --report /tmp/tjxy-new-2740-auto.json
```

目录必须全新；将 `--scan-concurrency` 改为 `1` 或 `4` 做同规模对照。运行期间避免主动启动编译，仍需记录主机外部负载。`stopped`、非零退出、扫描计数不全都不是通过。

本轮未执行远程存储、4K/高码率、长视频、转码、跨天稳定性或超过 2740 项容量测试。短时间数据库容量增长仍包含任务历史与 publication，不能据此推断完整保留周期后的增长。
